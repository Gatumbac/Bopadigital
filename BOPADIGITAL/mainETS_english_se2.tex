\chapter{INTRODUCTION AND PROJECT CONTEXT}

\section{Project Context}
BOHORQUEZ \& PAUTA CORP. BOPACORP S.A. is a business-to-business (B2B) telecommunications company. Sales advisors prospect for clients, schedule visits, manage negotiations, collect documents, and follow up on service activation. Supervisors and managers need updated information about sales, field activity, documents, and commercial performance.

Before BOPADIGITAL, many activities relied on spreadsheets, shared folders, messaging applications, and email. These separate tools made it difficult to keep one current view of each client and negotiation. BOPADIGITAL was created to centralize this commercial process.

The project context and initial requirements were established during Software Engineering I. The requirements document defined the problem, stakeholders, requirements, use cases, prototypes, and initial risks. The client accepted this baseline on November 4, 2025. During Software Engineering II, the team implemented the system through Scrum sprints and prepared the final documentation and deployment evidence.

\section{Problem Statement}
The initial analysis identified three operational bottlenecks in BOPACORP's commercial process:

\begin{enumerate}
    \item \textbf{Document delivery and operational delay:} Advisors collect contracts, identification documents, taxpayer information, and other files. Physical or separate delivery channels can cause office trips and delay the review.
    \item \textbf{Limited visibility of field activity:} Supervisors and managers lacked one view of visits, negotiation progress, and advisor activities. Monitoring depended on messages and manual updates.
    \item \textbf{Manual sales tracking and reporting:} Portfolios, negotiations, and performance indicators were managed in spreadsheets and manual reports. This made follow-up and decision-making more difficult.
\end{enumerate}

BOPADIGITAL addresses these problems through one platform for public information, commercial management, documents, and reports.

\section{Project Description and Evolution}
BOPADIGITAL combines a public website, an internal CRM, a mobile advisor application, a REST API, and shared TypeScript contracts and validation schemas. The public website provides services, contact, content administration, and employability workflows. The internal applications manage clients, negotiations, visits, documents, supervision, reports, and role-based access.

The mobile repository, \texttt{bopacorp-mobile}, uses Expo and React Native. It contains advisor routes for authentication, clients, negotiations, documents, and settings. The testing and demonstration chapters document the verified mobile workflows.

The project started with requirements and prototypes in Software Engineering I. In Software Engineering II, the team added quality checks, frontend and API tests, risk-based testing, deployment and installation guides, user manuals, and acceptance evidence.

\section{Project Objectives}
The general objective is \textbf{to digitize and centralize} BOPACORP's B2B commercial lifecycle to improve efficiency, information access, and management visibility.

The specific objectives are:

\begin{enumerate}
    \item \textbf{To support} the registration and management of corporate clients and commercial prospects.
    \item \textbf{To track} negotiations, visits, statuses, and relevant commercial observations.
    \item \textbf{To enable} advisors to manage field information and documents through web and mobile workflows.
    \item \textbf{To centralize} the review and approval status of documents required by the commercial process.
    \item \textbf{To provide} supervisors and managers with consolidated information for monitoring and decisions.
    \item \textbf{To offer} a public service catalog, a content management interface, and an employability workflow for external users and candidates.
    \item \textbf{To enforce} authentication, shared data contracts, quality checks, and repeatable deployment.
\end{enumerate}

\section{Project Scope and Exclusions}
The final scope is organized around the following components:

\begin{itemize}
    \item \textbf{Public Website:} company information, service catalog, contact, and employability workflows.
    \item \textbf{Content Management System:} authorized management of public content, catalog data, and media.
    \item \textbf{CRM:} role-based management of clients, negotiations, visits, documents, supervision, reports, organization, and employability.
    \item \textbf{Mobile Advisor Application:} advisor access to clients, negotiations, and documents through Expo/React Native.
    \item \textbf{REST API and Shared Contracts:} authentication, authorization, business services, validation, persistence, and TypeScript/Zod contracts.
    \item \textbf{Deployment and Documentation:} CI, deployment, installation, manuals, testing evidence, and client acceptance.
\end{itemize}

The client removed the Offer Matrices module from the final scope. Matrix construction, approval, subsidy calculations, and related calculations are excluded from the final features and scenarios. Historical references to this module are legacy material.

The final report includes only features in the agreed scope and supported by the evidence package. Other capabilities are limitations or future work.

\section{Stakeholders, Roles and Target Users}
The main stakeholders and target users are:

\begin{itemize}
    \item \textbf{Business Client:} views the catalog and contacts BOPACORP.
    \item \textbf{Sales Advisor:} manages assigned clients, negotiations, visits, and documents.
    \item \textbf{Supervisor or Sales Manager:} monitors advisors, progress, activities, and documents.
    \item \textbf{Documentation Coordinator:} reviews negotiation documents and updates their status.
    \item \textbf{Management or Executive Board:} consults reports and performance information.
    \item \textbf{Sales Advisor Candidate:} views vacancies and submits an application.
    \item \textbf{Web Administrator:} manages public content, catalog data, and CMS information.
    \item \textbf{Client Representative:} reviews sprint increments and signs acceptance records.
\end{itemize}

\begin{enumerate}

\subsection{Permission Enforcement}
The \emph{authenticate} middleware verifies the bearer token and loads the active user and roles. The \emph{authorize} middleware checks the permission required by the route. Permissions use the \emph{module.action} format, such as \emph{users.read} or \emph{catalog\_items.create}. Invalid identity returns unauthorized; missing permission returns forbidden.

Roles group permissions, while routes declare the required permission. Validation follows authorization. Services enforce ownership and state rules.

\section{Shared Contracts and Data Architecture}
The shared contract package is the integration boundary between the API and its clients. It provides common primitives, schemas, enums, and response wrappers. The package is published as \emph{@bopacorp/shared} and is consumed by the API, public website, CRM, and mobile repository.

The request flow has four steps. Routes select the endpoint and add middleware. Controllers handle HTTP data. Services apply business rules and run Drizzle queries. The database stores or returns data:

\begin{center}
\emph{routes} $\rightarrow$ \emph{controller} $\rightarrow$ \emph{service} $\rightarrow$ \emph{database}
\end{center}

The API uses one response envelope. Successful responses include data; paginated responses also include metadata; errors include \emph{success: false}, a stable code, and a message. This keeps client error handling consistent.
